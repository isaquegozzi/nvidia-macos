## Quantas etapas já existem no tinygrad?

- **10/10 cobertas genericamente (Ampere) em `tinygrad@e8c8ba1c`**: PCI detect, BAR mapping, BOOT0, GSP boot, MMU, VRAM, FIFO, GPFIFO, compute, DMA — todos têm implementação no caminho `PCIIface→NVDev→GSP→GPFIFO` (`nvdev.py:74-163`, `ip.py:19-661`, `ops_nv.py:363-728`, `system.py:58-90,160-307`).
- **0/10 com especialização `ga106`**: nenhum `device_id 0x2504`, `chip GA106`, SHA `ga106` ou quirk em `nvdev.py:114-116` / `ip.py:172-173,402,426-428`. GA106 é carregado como `GA1`/`ga102` por `architecture 0x17`. Único `GA106` no clone é a constante `NV2080_CTRL_MC_ARCH_INFO_IMPLEMENTATION_GA106` (`nv_570.py:23415`, `nv_580.py:24463`, `nv_610.py:25044`).
- **Nosso projeto: 1.5/10 (só passivo)**: PCI detect COBERTO, BAR mapping PARCIAL (só `start/end/flags` via sysfs, sem `mmap`), resto NÃO IMPLEMENTADO por design Fase 0 (`README` + `SAFETY.md`: sem escrita/MMIO/pushbuf/doorbell).

## Leitura do gap para GA106

1. O risco não está na enumeração (`0x2504` faz match) nem nos endereços (`0x1183a4`, `BAR1 0xb80f48/50`, `BOOT_0 0x00` são família, não SKU).
2. O risco está no **conteúdo dependente de FW/ctx**: `gsp/bootloader/booter_load` `ga102-570.144` + `golden ctx` (`GET_CONTEXT_BUFFERS_INFO` + `promote_ctx`) + `sm_86` (`_query_gpu_info`). Se o RM `570.144` tratar GA106 como `GA102` sem diferença, o caminho fecha; se houver `ucode/gr` específico, falha em `GSP_INIT_DONE` / `PROMOTE_CTX` / `SEND_PCAS_A` — só testável em HW (fora TG0).
3. `initialization-map.md` Etapas 0–3 (PCI→ctor→DRM→lazy init→POST/`fb_mem_unlock`) **não têm equivalente** no NVDev: ele assume GPU já POSTada por VBIOS/SBIOS e vai direto a WPR2→Falcon→GSP. Em lab, isso significa: nunca `unbind` sem `SAFETY.md`, nunca assumir `refcount`/runpm do Nouveau.
4. Próximo passo Fase 0 (só leitura): confirmar em HW passivo `boot0==0x176`/`arch 0x17` via `first-mmio-read.md` quando liberado, sem escrita; manter `ga106` como `UNCERTAIN` até lá.
