# NV stack map — `Tensor → … → GA106` (TG0, corrigido pelo source)

> Base: `tinygrad@e8c8ba1c7751142f7b20d85692afd2da5cef5e84` (`2026-09-04`), `tinygpu_releases@c0d024f9`.
> Método: análise estática em `/tmp/opencode/tg0-tinygrad`. Nada executado contra hardware.
> Hipótese inicial corrigida: a TinyGPU.app (DriverKit) **só mapeia BARs PCI e transporta MMIO/sysmem via socket**; o **check de arquitetura (`0xff00`/famílias, classes compute/GPFIFO/DMA) está no userspace** (`ops_nv.py`, `nvdev.py`, `nv/ip.py`). No macOS o caminho reutiliza o MESMO `NVDev→GSP→GPFIFO→compute` do Linux; o que muda é **transporte** (`APLRemotePCIDevice` vs `/sys/bus/pci`+VFIO) e **compilador** (Docker `cuda-arm64` vs nvrtc/nvjitlink nativo).

## Caminho real (uma linha)

```
Tensor (tinygrad/tensor.py)
 → Compiled._select_renderer/_select_iface (tinygrad/device.py)
 → Renderer: CUDARenderer | PTXRenderer | NVCCRenderer | NAKRenderer
 → Compiler: NVRTC/NVCC (CUDA C) | NVPTX/PTX (PTX) — no macOS via Docker ghcr.io/tinygrad/cuda-arm64:v2.3 / cuda-nvcc:12.8
 → cubin/PTX → elf_loader → NVProgram (+QMD) (ops_nv.py)
 → NVDevice (ops_nv.py) → iface NVK | PCI | MOCK
 → [macOS/TinyGPU] PCIIface → PCIIfaceBase → APLRemotePCIDevice → socket tinygpu.sock → TinyGPU.app (DriverKit BAR mapper)
 → [Linux]       PCIIface → PCIIfaceBase → PCIDevice → /sys/bus/pci + mmap BAR + VFIO
 → NVDev (nvdev.py): BAR0 MMIO, chip_id (BOOT_0/42), MMU/MemoryManager
 → FLCN[/COT] + GSP (nv/ip.py): boot Falcon, firmware ga102/ad102/gb202, RPC GSP (rm_alloc/rm_control), golden image, runlists
 → NVMemoryManager: VA 44-bit @0x1000000000, page tables, BAR1 VRAM vs sysmem
 → GPFIFO (compute_gpfifo / dma_gpfifo [/ vid_gpfifo]) + NVComputeQueue / NVCopyQueue (/ NVVideoQueue) + QMD + timeline signals
 → classes Ampere: AMPERE_CHANNEL_GPFIFO_A / AMPERE_COMPUTE_B / AMPERE_DMA_COPY_B
 → GA106 (Ampere, sm_86): chip_name GA1xx / fw ga102 / mmu_ver 2 — SEM quirk ga106-específico no clone (ver §10)
```

## Correções à hipótese (o que o source prova)

1. **TinyGPU.app não "suporta Ampere" sozinha.** `docs/tinygpu.md:9` (`Ampere+`) é requisito do *sistema tinygrad+TinyGPU*; a dext só expõe BARs via DriverKit. Quem decide família é `PCIIface (ops_nv.py:560)` + `pci_scan_bus (system.py:80)`; quem decide classes compute/DMA/GPFIFO é `NVKIface.setup_usermode (ops_nv.py:434-443)` no Linux e `NV_GSP.init_sw (ip.py:357-362)` no caminho PCI/GSP.
2. **macOS ≠ stack separada.** `System.list_devices (system.py:85)` troca apenas o transporte (`APLRemotePCIDevice`); `PCIIfaceBase (system.py:259-265)`, `NVDev`, `GSP`, `GPFIFO`, `NVCompute/CopyQueue` são os mesmos. `bdf_as_int (ip.py:602)` inclusive aceita `usb/remote` (`0x000`).
3. **`DEV=NV` no macOS significa `DEV=NV:PCI` na prática** (único iface sem `/dev/nvidia*`). `DEV=NV:NVK` é Linux-driver; `DEV=NV:MOCK` é teste (`ops_nv.py:583-586`, `device.py:370-377`, `docs/runtime.md:77-81`).
4. **Compilador é o outro acoplamento macOS.** NVRTC/PTX nativos não existem no macOS → `compiler_cuda.py:49,56,88,92` delegam a `osx_docker_cmd` (`ghcr.io/tinygrad/cuda-arm64:v2.3`); `extra/setup_nvcc_osx.sh` constrói `cuda-nvcc:12.8` + shims `~/.local/bin`. Sem Docker+`PATH` (`docs/tinygpu.md:43-53`), `Tensor→PTX/cubin` não fecha mesmo com PCI OK.
5. **`10de:2504` ≠ "GA106 verificado".** O match `0x2504&0xFF00=0x2500` (audit) prova enumeração; `sm_86`/GSP golden-image só se provam com `NV_PMC_BOOT_0/42` + `_query_gpu_info` em hardware real — fora do TG0. Não promover `YES` de PCI a "funciona".
